# script-to-video-studio 改动流程

这份流程存在的原因很具体：**这个项目的绝大多数返工都不是技术难度造成的，是猜需求造成的。**
真实发生过的（都在同一个工作会话里）：

| 我做的 | 用户的原话 |
|---|---|
| 顺手加了「用的是哪个分组哪个模型」的日志功能 | 「**我不是让你加这个功能**你先拉回到这个问题上」 |
| 把「画面里的文字」做成四个设置项 | 「**你这个复杂了**，实际上画面上的字都是要有的，我需要控制的只是有没有字幕」 |
| 并发测算按「每类活各自的上限」答了两遍 | 「我指的是 10 部**同时**跑并且是最高并发的情况下」 |
| 打完包才汇报 | 「**先不要打包**还有其他问题」 |
| 修参考图过滤只改了 4 处里的 2 处 | 「通用级的这个也有这个问题」 |

每一条的代价都是一整轮返工。而每一条**只要事先问一句就不会发生**。

## 何时用

在 `script-to-video-studio` 里：报 bug、要求修改、提新需求、问「这里为什么这样」。

**不适用**：打包、提交、跑测试、查一个事实、纯咨询。这些没有歧义，直接做。
这份流程不管别的项目。

---

## 一、先定性，别先动手

动手之前必须能把问题写成**一句带机制的话**。

```
不合格   「资产图没出来」                      ← 这是现象
不合格   「参考图有问题」                      ← 这是现象
合格     「第十一环节判定这条不出图，第十二环节
          又把它当参考图 —— 两个环节各自都对，
          凑起来做不出来」                     ← 这是机制
```

写不出机制就是还没定性。**这时候要做的是查，不是问，也不是改。**

能自己查到的一律自己查完再说话：

- 代码：哪一行做的判断、哪两份声明对不上
- 产物：`07_检查与记录/failures.json`、`execution_log.jsonl`、各环节的 json
- 用户给的排错包：解开来读，别只读文件名
- 配置：`config.json` 里的实际取值（**只读要用的那几个键，绝不回显密钥**）

拿这些去问用户，是把自己的活推给他。他手上有的是**意图**，不是我们的代码。

### 定性时必须回答的第三个问题：范围

这个项目有两套体系（电影级十七章 `n0..n14` / 通用十二环节 `s1..s12`）、
四类任务（资产图/场景状态图/故事板/分段视频）、两处 mapping、两个入口
（一键跑到底 / 单跑环节）。

**同一个毛病几乎从不只有一处。** 定性之后先数一遍：这个机制在几个地方成立？
「只改了 4 处里的 2 处」是这个项目里最常见的返工原因，没有第二名。

## 二、有歧义才问 —— 最多四个，写成 md

### 什么算歧义

判据只有一条：**不同的理解会导致做出不同的东西。**

```
要问    「集数按总时长算还是按剧本章节算」   → 两种答案做出来的是两个程序
要问    「这个新字段是给用户填的，还是程序算的」
要问    「这一条该停下来，还是记一条继续跑」
要问    「你要的是这一处，还是所有同类的地方都改」

不问    「用正则还是用 json 解析」            → 技术方案是我的活
不问    「变量叫什么」「放哪个文件」
不问    「n13 的输出里有没有 video_prompt」    → 代码里有答案，自己看
不问    「你确认要修吗」                       → 他已经说了要修
```

明显的直接做完再汇报：改错别字、补一条日志、修一个已经定性清楚且只有一种合理修法的 bug。
**硬问会变成噪音，而噪音会让真正该看的那次提问被跳过。**

### 一个问题合格的四条

1. **不同答案导致不同产物** —— 否则这个问题不该占一个名额
2. **给选项，并说清每个选项的代价** —— 「A 还是 B」是把判断推回去；
   「A（好处…风险…）还是 B（好处…风险…）」才是在帮他决定
3. **带上我的推荐和理由** —— 我读过代码，他没有。不给推荐等于浪费我掌握的信息
4. **只问意图，不问技术方案** —— 方案由我定，定错了是我的责任

四个是**上限，不是配额**。一个问题够就问一个。

### 问题文件

路径：`script-to-video-studio/决策记录/YYYY-MM-DD-<短横线短名>.md`（进 git）

```markdown
# <一句话说清这次要解决什么>

日期：2026-08-21
起因：<用户的原话，照抄，不改写>

## 我查到的

<定性结论：机制是什么。指到文件和行号。>
<范围：这个机制在哪几处成立。>

## 要你定的

### 1. <问题>

- **A（推荐）**：… —— 好处 … / 代价 …
- **B**：… —— 好处 … / 代价 …

我倾向 A，因为 <理由>。

### 2. …

## 你的回答

<留空，等填>
```

写完**停下来等回答**。不要一边等一边先改「反正肯定要改的部分」——
上一个问题的答案经常会把那部分也推翻。

## 三、实施

- **范围就是问清楚的那个范围。** 没问过的「顺手优化」一律不做 ——
  想做就下次问。用户的原话：「不要过度优化使得结果往外扩散无法控制」。
- 定性时数出来的那几处，**一处不落**。
- 跑全量测试，报确切数字（`py -m pytest`）。测试没过就没做完。
- 新增的检查如果会**拦住生产**，要能在页面上放行或说清怎么绕 —— 死路比漏检更糟。

---

## 四、交付：三处都要写

同一段内容写三处，因为读的人和读的时机不一样。

### 1. 对话里回复

用户当场要读的。**先说结论，再说为什么。** 不要复述我做过的步骤。

### 2. git 提交说明

跟着代码走，`git log` 里永远查得到。

### 3. 那份决策记录 md 的末尾

问题、回答、怎么修的、避免了什么 —— 四段在一个文件里，是一份完整案卷。
下次遇到同类问题，先搜这个目录。

### 「为什么会有这个问题」怎么写才算合格

要指到**机制**，而且要说清它为什么能长期存在而没人发现。

```
不合格   「之前的代码有 bug」
不合格   「没有考虑到这种情况」
合格     「check_keys 只查键在不在。模型返回 video_prompt: ""
          时键是在的，于是校验通过 —— 我们把空提示词落盘、
          当这一段做完了。而它在 capability_note 里写着
          VIDEO_PROMPT_RELEASE_BLOCKED，理由写得比我们能诊断
          出来的还清楚，我们一个字都没读。」
```

### 「修完能避免什么」怎么写才算合格

要说清**下次它会以什么形式表现出来**，而不是「更健壮了」。

```
不合格   「提高了稳定性」「减少了出错」
合格     「以前这一条会一路跑到成片：第十一、十二环节照跑（它们只看
          装出来的 SEG，看不出少了一个镜头），到第十三环节模型自己
          算出来、交一份空提示词，十七个环节的钱全白花。现在停在
          第十环节，报出是哪个镜头、在第几秒、没有容器装它。」
```

这一段是**验证我真的懂了**的地方。写不出「下次会怎样」，说明还没定性清楚，
回第一步。

## 这个项目的两条底线

1. **不报错的错最贵。** 这个项目所有 bug 里占比最高的一类是「不报错，只是少了或者错了」。
   修它们的方向永远是**把静默失败变成响亮失败**，不是让程序自己兜过去。
   兜过去的代价是几百步之后才发现，而那时候钱已经花了。

2. **判定做了、程序不认。** 反复出现的根因：某一环节在正文里说了决定
   （「本条不生成图片」「不生成视频执行计划」），而结构化字段里没有，
   程序信字段。查这一类时**同时读正文和字段**。
